# v2.20.0 - AKILI-SPECS methodology update

Release date: 2026-07-29

### Added

- **Users who never re-run the CLI can now hear about new versions — opt-in, at session start.** The update banner already existed, but it only fired when someone ran `akili`, which after installation is almost never: the methodology runs inside Claude Code/OpenCode sessions, not through the CLI. Three pieces close the loop: **(1)** the registry check is now **cached for 24h** (`~/.akili-specs-update.json`) and skipped entirely for non-TTY runs — previously every single CLI invocation paid up to 1.5s of registry latency; **(2)** a new **`akili check-update`** subcommand prints one plain line when a newer version exists and, with `--quiet`, stays silent and exits 0 when current — built to be hook-safe (a hook that can fail or spam is worse than no hook), with the update line phrased for the agent reading session context (*"Tell the user to run: akili update"*); **(3)** a new **`akili notifications enable|disable|status`** command registers that check as a **SessionStart hook** in Claude Code's `settings.json` — strictly opt-in (installing hooks uninvited would violate the same ethos as skip-by-default), surgical on disable (removes exactly its own hook, leaves every other setting untouched), and it **aborts without writing when `settings.json` is not valid JSON**. Verified end-to-end against a scratch settings file: enable/idempotence/status/disable preserving foreign hooks, the corrupt-JSON guard, cache write, and the quiet line under a simulated newer version. OS-level notifications (launchd/cron + toasts) were considered and rejected as disproportionate for a methodology package. Claude Code only for now — OpenCode/Antigravity hook mechanisms differ. The install summary now mentions the option.
- **`.claude/` now explains itself to contributors.** The directory name reads as Claude-only configuration, but it is the canonical source for **all three install targets** — a contributor wanting to improve the OpenCode or Antigravity experience could reasonably not find where to edit, or worse, propose a per-tool copy. Renaming was evaluated and rejected: the path is load-bearing three ways (this repo **dogfoods its own methodology** — Claude Code sessions load the `/akili-*` commands and skills from that literal path; the installer reads it as its source; the npm package ships it), and a symlink alias would punish Windows contributors. The fix is signposting at every place a contributor lands: a new `.claude/README.md` (1.7kB — npm ships README files at any level regardless of `files`, verified with `pack --dry-run`, which conveniently also explains the layout to anyone inspecting the tarball), a *Why Everything Lives Under `.claude/`* section in `CONTRIBUTING.md`, and one-line notes in `README.md` § Repository Structure and `AGENTS.md` § Repository Purpose. All four say the same thing: edits for any target happen here; there is no per-tool copy to keep in sync.
- **The release Slack notification now tells existing installs how to update.** It only said `npm install -g akili-specs` — correct for a first install, but the audience of a release announcement is mostly people who already have it. Added the second line: `akili update` (which itself runs `npm install -g akili-specs@latest` and then refreshes the installed commands, skills, and templates — verified against `runUpdate` before promising it). Payload validated with `--dry-run`.
- **A send that returned is not a send that was received.** Field lesson from driving the Antigravity CLI through a terminal: `terminal wait --for tui-idle` is satisfied **before** the TUI actually accepts input, so a prompt fired on that signal can vanish without an error — the readiness primitive answers *"is the process quiet?"*, not *"did the input land?"*, and a TUI can be quiet precisely because it has not accepted the input yet. `leader.md`'s cross-host dispatch section already cataloged the silence failure one level up (a group address with no members accepts a dispatch and delivers it nowhere); this is the same class at the transport layer, and it gets the same rule: **verify delivery at the target** — after sending, read the target's buffer back (`terminal show`) and confirm the prompt landed before spending a wait on work that may never have started. Every layer that can accept without delivering needs its own receipt check.
