# v2.28.0 - AKILI-SPECS methodology update

Release date: 2026-09-29

### Changed

- **Model-routing guidance recalibrated for the current Opus generation, and workers no longer stop short of a task's end (`changes/opus-5-5-rebaseline`).** `docs/model-routing.md`'s Opus guidance is rewritten for the newer model: the vendor's own published starting point for open-ended agentic work is now a mid-range effort level, so the old "start high and iterate down" advice is removed; the previous generation's higher starting points survive only as a labeled historical reference, not as current practice. This is vendor guidance, not a result AKILI has measured on its own specs — the doc says so explicitly (`AKILI-measured: none yet`) and leaves open, pending a future sweep, whether the methodology's own Implementer/Reviewer effort defaults still earn their cost under the new generation. The doc also documents an optional time-signal capability some harnesses can offer (an elapsed-time line a harness can append to what the model sees, advisory only; the doc says not to attach it to a Reviewer's turn) — a note for maintainers wiring a custom harness; no packaged persona or command emits or reads it. Separately, the Implementer and Tester personas (`implementer.md`, `tester.md`) gain a **"don't stop short"** rule: a worker must not end its turn with a premature stop — an announced next step with no action taken, an unprompted offer to keep going, or stopping because the turn ran long. Each persona names its legitimate stops: for the Implementer, a truthful partial with a named blocker, a blocker only the user or Leader can clear, a deliberately protected blocker, a pending confirmation on a destructive or irreversible action, or genuine completion; for the Tester, its existing `PASS` / `PRODUCT_BUG` / `AUTOMATION_DEFERRED` / exhausted-retries outcomes, with a pending destructive confirmation as a "never override" guard rather than a stop. To match, `/akili-execute`'s handling of a worker's `Not Done / Assumptions` report is split three ways: a named blocker still escalates as before; under the `pre-approved` running mode, a report naming owed work with no blocker is automatically re-spawned to finish it, capped at two such continuations per task before it escalates like a blocker; under `gated` mode, behavior is unchanged. Continuations are tracked separately from the existing 3-attempt rework ceiling and never consume one of its attempts.
- **`/akili-specify` gains a design rule for mechanisms named by a requirement (kaizen apply, `changes/review-intensity-routing`).** When a requirement names the step, list, or check that delivers an obligation at a gate, the author confirms in the command text that the step runs before the gate it guards.
- **`/akili-specify` gains a design rule for rules keyed to a field's states (kaizen apply, `changes/premise-ledger`).** When a requirement or design gives a reader one action per state of a cell, status, or field, every state the field can hold is listed first, including states another rule forbids, and each gets an action or a stated fall-through.
- **`/akili-execute`'s Pivot Protocol reads the diff of each amended document (kaizen apply, `changes/premise-ledger`).** After the two-direction sweep, the Leader reads the `git diff` of every spec document the pivot amended and confirms each removed line was intended; the sweep finds stale values, not a heading or clause the edit destroyed.
- **`/akili-specify` gains a task-quality rule for lists ported between roles (kaizen apply, `changes/opus-5-5-rebaseline`).** When a requirement copies a list into another role's persona, the list is re-derived from that role's contract: items only the source role can take are dropped, and an exhaustive list must still name the role's success outcome.
