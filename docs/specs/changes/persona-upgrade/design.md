## 2. Executive Summary

Three mechanisms on one file format. The templates gain markers; a parser in `bin/akili.js` turns any persona into a list of segments; the state report, the fix, the migration and Safe Update are operations on that list. The CLI compares against its own packaged templates and a **dense** digest table — every section's hash at every release — so an unchanged section is `current` and an old one is `outdated` without shipping any old text. A legacy table seeded from every tagged release lets the migration recognize personas scaffolded long before the markers.

## 3. Architecture Overview

```text
.claude/templates/<role>.md        marked: owned sections + one project block
.claude/templates/digests.json     dense: role → id → release → sha256, every release; plus legacy: role → id → tag → sha256
              │ packaged; installed as one more resource file (S1)
              ▼
bin/akili.js  doctor --agents [--fix] [--section <id>]… [--allow-branch] [--force] [--dry-run] [--tool <t>]
   parsePersona(text)        → {eol, frontMatter, segments[], migrated}     segments: owned | project | text
   sectionStates(...)        → current | outdated | custom-edited | missing | unlocated | extra | unreadable | unmarked
   guards(...)               → branch (kaizen resolution) · dirty tree · dry-run
   applyFix(...)             → new text + change list (pure)
   migratePersona(...)       → fenced (exact) | fenced (heading) | not located (pure)
   runAgentsDoctor(args)     → read → guards → backup → write once → re-report → exit code
              ▲
/akili-constitution Safe Update ── runs the CLI when on PATH; otherwise the same rules by hand from the installed templates + digests
/akili-audit ── its existing persona structural check (item (c)) now uses the same states
```

## 5. Data Model

### 5.1 Marker grammar

| Element | Form | Rule |
|---|---|---|
| Section open | `<!-- akili:section id=<id> since=<vX.Y.Z> -->` | Own line; `id` `[a-z0-9-]+`; `since` a release tag |
| Section close | `<!-- /akili:section -->` | Own line |
| Project block | `<!-- akili:project -->` … `<!-- /akili:project -->` | Exactly one per persona; empty in templates |
| Migration record | `<!-- akili:migrated <release> not-located=<id,id\|none> -->` | Own line, at most one, placed **immediately before the project block's open marker**. AKILI-owned metadata, not project space |
| Body | Lines between open and close | Compared after normalization: `\r` stripped, trailing whitespace stripped per line, one trailing newline |

Line endings: the parser strips `\r` before matching; the writer emits the file's majority line ending, so a CRLF persona stays CRLF. Front matter: a leading `---` … `---` block is one text segment; a marker inside it is ignored. Nesting is not allowed. A persona is `unreadable` when an open has no close, a close has no open, a section opens inside another, an id repeats, the project block count is not one, or two migration records exist. **Exception:** a persona with **no** marker of any kind is `unmarked`, never `unreadable`, whatever its project-block count (a pre-marker persona has none).

### 5.2 Section ids (the closed set at this release)

| Template | Sections, in file order | Level |
|---|---|---|
| `implementer.md` | `context-alignment` (item 1) · `scope-discipline` (2) · `craft` (3) · `verification` (4) · `reporting` (`## 📝 Reporting Completion`) · `shared-file-discipline` (`## 🔒 …`) | items; `##` |
| `reviewer.md` | `read-only-role` (1) · `audit-checklist` (2) · `structured-evaluation` (3) · `lenses` (4) · `depth-scaling` (5) · `review-output` (`## 📝 Structured Review Output`, its `### Option` subsections included) | items; `##` |
| `tester.md` | `context-alignment` (1) · `prove-behavior` (2) · `incremental-focus` (3) · `bounded-loop` (4) · `test-report` (`## 📝 Structured Test Report Output`, `###` included) | items; `##` |
| `leader.md` | `primary-instructions` (items 1–4 as one) · `delegation` (`## 📏 Delegation Thresholds` through its last `###`, *Deferring a check*) · `test-harness` (`## 🧪`) · `reporting` (`## 📝`) · `shared-file-discipline` (`## 🔒`) | `##` |

Each section's **level** is the level of its first line: an item (`N. **…**` at column 0) or a `##` heading. A `##` section runs to the next `##`; an item section runs to the next item at column 0 or the next `##`. `###` headings never end a section. Unfenced in every template, and the complete allowed list for FR-1: the title, the intro paragraph, the model-tier note, `## 🎯 Primary Instructions` heading lines, `---` rules, blank lines, the project block, the migration record, `## Authorship`.

### 5.3 `digests.json` *(ADR, DD-3)*

```text
{ "version": "2.30.0",
  "releases": { "2.30.0": { "implementer": { "verification": "<sha>", … }, … }, "2.31.0": { … } },
  "legacy":   { "implementer": { "verification": { "v2.27.0": "<sha>", "v2.29.0": "<sha>" }, … }, … } }
```

- `releases` is **dense**: every section of every role at every release since the markers, whether or not it changed — twenty-two hashes per release, appended by the release step. It is consulted only to recognize an *earlier* text: `current` is decided by comparing with the packaged template itself, so the table never needs an entry for the release being developed.
- `legacy` holds the pre-marker texts: for every git tag whose tree holds `.claude/templates/<role>.md` (the first is `v0.5.0`; 79 tags exist up to `v2.29.0`), each section's body as cut from that tag's template by the level rules of §5.2, hashed. Seeded once by T1 with `git show <tag>:.claude/templates/<role>.md`; a tag whose template lacks a section simply has no entry.
- `version` is the release that wrote the file. `since=` attributes in the templates are rewritten by the release step for sections whose hash changed against the previous release.

### 5.4 Section state (FR-3), as computed

| Input | State | `--fix` |
|---|---|---|
| Persona hash = the packaged template section's hash, computed at run time | `current` | nothing |
| Persona hash ≠ the packaged one and = some `releases[r]` or `legacy` entry | `outdated` (report the release matched) | replace body; rewrite `since=` |
| Persona has the id, hash matches nothing | `custom-edited` | skip, unless `--section id` |
| Persona has ≥ 1 marker, lacks the id, and the id is not in the migration record | `missing` | insert (DD-4) |
| Persona lacks the id and the migration record lists it | `unlocated` | skip, unless `--section id` — then insert and remove the id from the record |
| Persona has an id the template lacks | `extra` | nothing |
| Grammar violation (5.1) | `unreadable` | skip the file; report |
| No marker at all | every id `unmarked` | migrate (DD-6) |
| Persona file absent | `absent` (file) | install the packaged template with an empty project block |
| `.agents/` absent | one line; exit 1 | nothing |

Exit code: 1 when any `outdated`, `missing`, `unmarked`, `unreadable`, or an `absent` persona; **0** otherwise — `custom-edited`, `extra` and `unlocated` are decisions a maintainer owns and do not fail CI. A second run after `--fix` therefore exits 0 (FR-4 idempotence as amended).

## 6. CLI Surface

| Flag / command | Behavior |
|---|---|
| `akili doctor --agents` | Report only; prints the CLI release compared against and the detected tool root for information |
| `--fix` | Guards (DD-12), backup, then one write per persona: replace `outdated`, insert `missing`, migrate `unmarked`, install `absent` |
| `--section <id>` (repeatable; `parseArgs` `multiple: true`) | Lets `--fix` replace a `custom-edited` or insert an `unlocated` section with that id |
| `--allow-branch` | Overrides the branch guard; printed in the report |
| `--force` | Overrides the dirty-tree guard (existing flag, new meaning under `--agents`) |
| `--dry-run` | Runs the guards and prints the full plan and exit code; writes nothing, no backup (existing flag; `doctor --fix` without `--agents` keeps ignoring it) |
| `--tool <t>` | Names the tool root printed; no effect on states |
| Without `--agents` | Byte-for-byte the old behavior |

Report rows follow the existing doctor style: per persona a header, then `STATE  <id>  (since vX · matched vY)`, then the persona summary; totals and exit code last. `--fix` rows: `FIXED`, `INSERTED`, `INSTALLED`, `FENCED (exact|heading)`, `NOT LOCATED`, `SKIPPED (custom-edited; use --section)`, `MOVE <injection> from <id> to the project block`, `BACKUP <path>`, `REFUSED (<guard>)`.

## 7. Backend Module Design (`bin/akili.js`)

| Function | Responsibility |
|---|---|
| `parsePersona(text)` | Detect EOL; split front matter; scan markers with a strict regex after `\r` strip; segments with spans; migration record; grammar check |
| `normalizeBody`, `hashBody` | §5.1; sha256 via `crypto.createHash` |
| `loadTemplates()` | `SOURCE_TEMPLATES` + `digests.json` (packaged) |
| `sectionStates(persona, template, digests)` | §5.4 (pure) |
| `applyFix(persona, template, digests, opts)` | New text + change list; updates the migration record on `--section` insertion (pure) |
| `migratePersona(text, template, digests)` | DD-6 (pure) |
| `resolveBranchContext(cwd)` | DD-12: the kaizen resolution, in code |
| `runAgentsDoctor(args)` | I/O: read, guards, backup, atomic write (temp + rename, the file's helper), print, exit code |

The pure functions live in one module, `bin/persona.js`, required by `bin/akili.js` and by `scripts/release.js` (which cannot require `bin/akili.js`: that file runs `main()` on load). `bin/` is in `package.json` `files`, so the module ships.

Argument plumbing: `agents` (boolean), `section` (string, `multiple: true`), `allow-branch` (boolean) join the `parseArgs` options literal and the `args` mapping; `doctor` dispatches to `runAgentsDoctor` when `args.agents` is set.

## 8. Design Decisions

### DD-1: Item-level sections in the workers, five coarse sections in the Leader

As §5.2. A section's end is defined by its level, never by an internal `###` (S3). **Rejected:** per-`###` sections in the Leader; one section per file.

### DD-2: Injections and hand additions go to the project block; the project block wins; nothing is injected twice

Every *Injection scope* row writes a labeled line into the project block. The last bullet of `context-alignment` / `primary-instructions` says the project block overrides any sentence in a marked section. Safe Update writes an injection only when the persona does not already carry it anywhere; an injection found inside a `custom-edited` section is reported as `MOVE`, never duplicated (challenge point 7).

### DD-3: A dense digest table plus a legacy table, generated at release time *(ADR)*

- **Issue.** Tell "the v2.29 text" from "someone edited this" without shipping old texts; recognize personas scaffolded on any past release.
- **Decision.** `releases` is dense (§5.3): the release step writes every section's hash under the new version and rewrites `since=` only where the hash changed. `legacy` is seeded once from every tag by T1 and never touched by the release step. The release step stages every file it wrote (four templates when any `since=` changed, plus `digests.json`) and prints them in the `git add` hint. No drift test runs in `npm test` (a template edit is red until release by construction); instead `scripts/release.js` asserts, before the bump, that every template section parses and that the previous release's table is intact, and `release:status` reports a `digests.json` whose `version` differs from `package.json` as drift.
- **Consequences.** `current` is one lookup; `outdated` names the release; the seed makes this repo's own older persona and STAR's locatable by exact match where their text is any past release's. Twenty-two hashes per release stays small.
- **Rejected:** a sparse table (S2); deciding by `since=`.

### DD-4: Fix is pure, then written once

`applyFix` returns the new text and change list; `runAgentsDoctor` writes the backup, then the file once (temp + rename), then prints. Replacement keeps the marker lines and rewrites `since=`. Insertion of a `missing` section goes after the persona's segment for the template's preceding section; when that is absent, before the next present one; when neither exists, before the project block (a marked persona always has one, else it is `unreadable`). `--section` on an `unlocated` id inserts the same way and removes the id from the migration record. `absent` personas are installed from the packaged template, project block empty.

### DD-5: Backup in `.agents/.backup/`, ignored locally, excluded from the dirty check

`.agents/.backup/<role>.md.<YYYYMMDD-HHMMSS>`; `.agents/.gitignore` gains `.backup/` (created when missing). The dirty-tree guard (DD-12) ignores `.agents/.gitignore` and `.agents/.backup/`, so the fix's own artifacts never trip it; the rewritten personas do, by design — the report ends with "commit `.agents/` before the next `--fix`, or pass `--force`".

### DD-6: Migration — locate section starts, then cut by level

For an `unmarked` persona: (1) split front matter off; (2) for each template section, find its **start line**: exact — a run of lines whose normalized body hashes to any `releases` or `legacy` entry; else heading — a line equal, after stripping list numbers (one or two spaces), emoji, punctuation and case, to the section's first line **in any release or legacy text**, followed within three non-empty lines by a line whose first 40 normalized characters equal that text's opening sentence's; (3) each located section runs from its start to the next line that starts a section of the same or higher level (§5.2: `##` for both; an item at column 0 for items), or to the project block, `## Authorship`, or end of file; `###` never ends it; (4) sections not located are reported and recorded; (5) the project block is inserted after the last fenced section; when nothing was fenced, at end of file, or before `## Authorship` when it exists; (6) the migration record goes immediately before the project block. Front matter and every unfenced line stay in place; nothing is reordered. Retitled items (STAR renamed items 1 and 2) are located by exact body when their text is a past release's, else `not located`. **Rejected:** fuzzy scores; stopping at any heading (S3).

### DD-7: Safe Update delegates to the CLI; the prose names the states

Step 8B's Safe Update bullet: when `akili` is on PATH, say to run `akili update` first, then run `akili doctor --agents --fix` and read its report; otherwise apply the §5.4 states by hand from the installed templates and `digests.json` (installed by DD-11). "Append a minimal upgrade block" is removed. The inline-draft path ("draft equivalent personas inline") now drafts with markers and an empty project block. Surfaces 10–13 carry the sentences that turn false.

### DD-8: The audit's existing structural check adopts the states

`akili-audit.md` item (c) already compares persona structure to the installed templates; it now runs `akili doctor --agents` (or reads the states by hand), reports counts by state, and names `--fix` as the remedy. Both "never an overwrite" sentences are rewritten: a manual trim for injection bleed; the CLI for drift. No second row (W11).

### DD-9: Tests with `node:test`, fixtures as files

`"test": "node --test"`. Pure-function tests over the seven fixtures (FR-9); one I/O test in a temp dir asserts the backup exists and the persona is byte-identical after a forced write failure (a read-only target), and that the write lands when allowed. CI runs `npm test`. Each test is written red first.

### DD-10: The CHANGELOG entry — content

Headline; what a maintainer runs (`akili update`, then `akili doctor --agents --fix` in each project, on the apply-capable branch); the section ids; the seeded legacy table; classification **minor**; the convention going forward. It replaces nothing in the v2.29.0 note.

### DD-11: `digests.json` is a resource file

The installer's resource copy list and `doctorTool`'s resource checks gain `templates/digests.json` (the four templates are copied through `AGENT_TEMPLATES`, a fixed list that stays as it is); `scripts/ci/install-layout-regression.js` expects it. `akili update` then refreshes it with everything else. Step 8E wrappers, the personas' rules and the install targets are unchanged.

### DD-12: `--fix` resolves the branch the way the kaizen skill does, and refuses when it cannot

`resolveBranchContext`: `Integration Branch:` pin → apply-capable is that branch; else `Default Branch:` pin; else `git symbolic-ref refs/remotes/origin/HEAD`; else the unique `main`/`master` among local and `origin/` branches; **unresolved → not apply-capable → refuse** (the kaizen rule: deferring is always safe). `--allow-branch` overrides and is printed. Not a git checkout → no branch exists → proceed, say so. Dirty guard: `git status --porcelain -- .agents` minus `.gitignore` and `.backup/` non-empty → refuse unless `--force`. `--dry-run` runs both guards and reports what they would do.

### DD-13: The migration record is owned metadata outside the project block

The record line sits immediately before the project block (§5.1), so `--fix` may rewrite it without touching project space; `--section <id>` insertion removes the id; an empty record (`not-located=none`) stays as a marker that the migration ran. After a migration, not-located ids are `unlocated` (exit 0) until the maintainer moves the old text and runs `--section`.
