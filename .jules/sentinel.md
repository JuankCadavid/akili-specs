## 2026-07-29 - Uncontrolled Resource Consumption in NPM Registry Checks
**Vulnerability:** The CLI fetches package updates from the npm registry using `https.get` but does not bound the size of the HTTP response or properly dispose of unread stream chunks on error statuses.
**Learning:** This exposes the tool to Uncontrolled Resource Consumption (DoS) and potential socket memory leaks if the registry responds unexpectedly or maliciously.
**Prevention:** Always implement a maximum chunk length check in `res.on('data')` when consuming external data, call `req.destroy()` to abort oversized streams, and remember to call `res.resume()` on error paths to release socket resources.
## 2026-07-30 - Arbitrary File Overwrite via Symlink Attack
**Vulnerability:** The `install` command used `fs.cpSync` and `fs.copyFileSync` with `--force` without unlinking symlinks, potentially allowing an attacker to overwrite arbitrary sensitive files on the user's filesystem (like `~/.ssh/authorized_keys`) if they place a symlink in the target directory (e.g., `~/.claude/commands/akili-audit.md`).
**Learning:** When writing files recursively and allowing existing files to be overwritten, using `fs.cpSync` or `fs.copyFileSync` on a symlink target rewrites the referenced file rather than replacing the link. Checking existence with `fs.existsSync` is not enough because it follows symlinks.
**Prevention:** Use `fs.lstatSync` to check if a file exists, and if it is a symbolic link, remove it first using `fs.rmSync(targetPath, { force: true })` before copying.
## 2026-08-02 - Regex Engine Stack Exhaustion in ANSI Escape Stripper
**Vulnerability:** `scripts/parse_tests.js` ran its ANSI-stripping regex over unbounded `failureMessages` input. A multi-megabyte message exhausts the regex engine's backtrack stack (`RangeError: Maximum call stack size exceeded`), crashing the report step.
**Learning:** Measured on a ~10MB adversarial payload, the failure mode is input size, not pattern shape: the naive regex and the community-hardened `strip-ansi` pattern both throw the same `RangeError`, and both run in ~1ms on bounded input. Swapping the regex alone does not fix the crash.
**Prevention:** Bound unbounded input BEFORE running any regex over it (here `.slice(0, 2000)` ahead of the 120-char output truncation) — the same bound-every-external-read principle as the 2026-07-29 registry fix. Keep the community-hardened pattern as defense in depth against true backtracking blowups.
## 2026-08-03 - Shell Evaluation Hardening: execSync → execFileSync
**Vulnerability:** `bin/akili.js` built package-manager and version-check commands as shell strings for `child_process.execSync`. Review note: every interpolated value comes from a hardcoded whitelist (`npm`/`pnpm` — the user agent only selects probe order) or a literal, so there is no attacker-controlled input and no actual injection today; this is hardening against future call sites, not an exploitable CWE-78.
**Learning:** `execFileSync` with an args array removes the shell from the equation — but on Windows, patched Node (CVE-2024-27980) throws `EINVAL` when spawning `.cmd`/`.bat` without `shell: true`, so a naive swap silently breaks `npm.cmd`/`pnpm.cmd` invocation on modern Node.
**Prevention:** Prefer `execFileSync(bin, args)` over shell strings for anything dynamic; on `win32` pass `shell: true` (safe here because every argument is a static literal — never do this with untrusted args). Route stderr with `stdio` instead of `2>/dev/null` so the command stays shell-free on POSIX.
## 2026-08-04 - Symlink Defense Depth for Recursive Copies and File Writes
**Vulnerability (as reported):** nested destination symlinks inside directories copied by `fs.cpSync`, plus unprotected `fs.writeFileSync` targets (`~/.akili-specs-update.json` cache, Claude Code `settings.json`).
**Learning:** The behavior is **runtime-version-dependent, proven by the CI probe across the matrix**: on Node 18.20.8 (linux/darwin/win32), 20.11.1, and 22.12.0, `fs.cpSync(force)` *replaces* a nested destination symlink — the attack does not reproduce. On **Node 22.23.1 (all three platforms) it writes THROUGH the nested destination symlink** — the attack is real on current Node 22.x; the semantics changed inside the 22.x line. A single-version measurement (the reviewer's first pass) and an unmeasured assertion (the report) were both wrong in opposite directions; only the executed matrix held the truth. `fs.writeFileSync` follows destination symlinks on every version, so the cache/settings guards are unconditional hardening.
**Prevention:** Keep `removeTargetSymlinks` ahead of recursive copies (verified effective on all 6 matrix combinations), guard every `writeFileSync` destination with an `lstat` check, and pin filesystem semantics with the CI probe (`scripts/ci/install-symlink-probe.js`) — it asserts the defense and records raw `cpSync` behavior per platform/Node, so the next silent runtime change surfaces in CI instead of in the field.
## 2026-08-05 - TOCTOU Symlink Attack on File Writes
**Vulnerability:** The CLI checked if a target was a symlink using `fs.lstatSync` and removed it, and then subsequently called `fs.writeFileSync` to write to the cache or settings file. This introduced a Time-of-Check to Time-of-Use (TOCTOU) vulnerability where an attacker could create a symlink in the window between the `lstatSync` check and the `writeFileSync` operation, allowing them to overwrite arbitrary files on the filesystem.
**Learning:** Checking for and removing a symlink prior to a write operation is fundamentally flawed because it is not atomic. If the filesystem changes between the check and the write, `fs.writeFileSync` will blindly follow the symlink that an attacker managed to place there. Severity reported HIGH; realistically **LOW** — winning the race requires an attacker who can already create symlinks inside the user's home and `.claude/`, a position from which the race adds nothing (same reclassification pattern as the PR #3/#4 findings). Merged as hardening: the atomic write also buys **crash-safety** — a `settings.json` can no longer be left half-written by an interrupted process — which is arguably the more valuable property.
**Prevention:** Always use atomic operations when writing sensitive data. Write the data to a temporary file in the same directory (with a randomized name using `crypto.randomBytes`, opened `wx` so a pre-existing entry at the temp path fails the write instead of being followed) using `fs.writeFileSync`, and then use `fs.renameSync` to move it over the destination target. `fs.renameSync` replaces symlinks rather than following them, securely mitigating the TOCTOU attack.
## 2026-08-06 - TOCTOU Symlink Attack on File Copies
**Vulnerability:** The CLI checked if a target was a symlink using `fs.lstatSync` and removed it, and then subsequently called `fs.copyFileSync` in `copySingleFile`. This introduced a Time-of-Check to Time-of-Use (TOCTOU) vulnerability where an attacker could create a symlink in the window between the `lstatSync` check and the `copyFileSync` operation, allowing them to overwrite arbitrary files on the filesystem.
**Learning:** Same non-atomic check-then-copy flaw as the 2026-08-05 write-path finding, on the remaining raw `fs.copyFileSync` call site. Severity reported anywhere from LOW to CRITICAL across twelve duplicate Sentinel PRs (#9–#20) for this one finding; realistically **LOW** for the same reason as 2026-08-05 — the attacker must already control the destination directory. Merged as hardening plus crash-safety. Process learning: the Sentinel automation re-files the identical fix daily when its PR cannot merge (required review unsatisfiable because the bot authors PRs under the owner's account); the daily run needs a dedup/backoff or the finding must be fixed at the source promptly.
**Prevention:** Always use atomic operations when copying sensitive files. Copy to a temporary file in the same directory (randomized name via `crypto.randomBytes`, `fs.constants.COPYFILE_EXCL` so a pre-existing entry at the temp path fails the copy instead of being followed), then `fs.renameSync` over the destination — `renameSync` replaces symlinks rather than following them.
## 2026-09-04 - TOCTOU Symlink Window on Recursive Directory Copies (and script writes)
**Vulnerability:** `copyDirectoryContents` in `bin/akili.js` ran `removeTargetSymlinks` and then `fs.cpSync(force)` for every top-level entry of `commands/` and `skills/`. On Node 22.23.1 `cpSync` writes THROUGH a nested destination symlink (2026-08-04 matrix), so a link (re)created between the check and the copy would redirect the packaged content over an arbitrary file. Separately, `scripts/parse_tests.js` and `scripts/release.js` still used raw `fs.writeFileSync`, which follows a destination symlink on every Node version.
**Learning:** Third instance of the same non-atomic check-then-write shape (2026-08-05 writes, 2026-08-06 single-file copies); this was the last `cpSync` call site. Severity reported LOW→CRITICAL across ten duplicate Sentinel PRs (#21–#30) for two findings; realistically **LOW** — the attacker must already own the destination directory (`~/.claude`, `~/.config/opencode`), from which the race adds nothing. Merged as hardening plus crash-safety. Process learning repeats: the automation re-filed the identical fix daily for nine days because self-authored PRs cannot satisfy required review; the fix has to land at the source promptly, and the daily run still needs dedup/backoff.
**Prevention:** Never hand a destination path to a primitive that follows symlinks. Replace `fs.cpSync` with an explicit walk (`copyTreeSync`): `mkdirSync` for directories after unlinking any non-directory squatting at the path, `atomicCopyFileSync` (COPYFILE_EXCL temp + `renameSync`) for every leaf. Apply `atomicWriteFileSync` to every script write, not only the shipped CLI. The CI probe now asserts the leaf copy replaces a symlink even WITHOUT the prior `removeTargetSymlinks` pass — the property the TOCTOU argument actually depends on.
## 2026-09-20 - Missing Response-Stream Error Handler in the Update Check
**Vulnerability:** `fetchLatestVersion` in `bin/akili.js` attached `error` and `timeout` handlers to the request (`req`) but none to the response stream (`res`). When the registry connection drops after headers, `res` emits `error` (`ECONNRESET`) while `req` emits only `close` — so the existing `req.on("error")` never fires and the promise is left with no settling path. Since `await checkForUpdates()` runs before every command, the CLI stops responding.
**Learning (corrected — the reported mechanism does not reproduce):** The PR, and all eleven duplicates that filed it, described this as an unhandled `error` event crashing the process, a `CRITICAL` DoS. **Measured on Node v22.12.0 against a server that sends headers plus a partial body then destroys the socket, it does not crash.** Event order with a listener attached: `res:data | res:aborted | req:close | res:error(ECONNRESET) | res:close`. With **no** `res` error listener the process does **not** throw — deterministic across three runs: the error is swallowed and the promise **never settles**. The failure is a **hang, not a crash**, which also means no stack trace and nothing in logs — quieter to diagnose than the reported crash would have been. Severity is **LOW**, not `CRITICAL`: the `!process.stdout.isTTY` early return means scripted and CI runs never make the call, the 24-hour cache bounds it to once per day, and deliberately triggering it requires MITM of `registry.npmjs.org`. The half of the report that was right — `req.on("error")` does not cover `res` — is the whole of the real defect, and the fix is correct as written. Same lesson as 2026-08-04: an unmeasured assertion in the report was wrong, and only the executed probe held the truth.
**Prevention:** Attach `.on("error", ...)` to the response stream as well as the request, and have it `resolve`/`reject` — a handler that only logs still leaves the promise pending. Verify such a fix with a **falsifier**, not a green run: strip the handler and confirm the harness hangs, then restore it and confirm it settles. Both were executed here (hangs without, resolves `null` with).
**Process (third occurrence, still unfixed):** The automation re-filed this identical one-line fix **daily for eleven days** as PRs #31–#41, then filed **#42 the day after #41 merged**. The 2026-08-06 entry recorded the same loop for #21–#30 and named the cause — self-authored PRs cannot satisfy required review, so nothing ever closes the finding from the bot's side. Two consecutive batches, twenty-one duplicate PRs, and the dedup/backoff gap is **outside this repository**: there is no bot configuration here to change (`.jules/` holds only this log; no workflow references it). The lever that exists in-repo is this file, which the automation reads — hence this paragraph. The durable fix belongs in the Jules/Sentinel job: suppress a finding already open as a PR, and back off after a rejection instead of re-filing on a fixed daily cadence.
## 2026-09-25 - Missing Response-Stream Error Handler Due To Early Return
**Vulnerability:** In `fetchLatestVersion`, the response stream event handler (`res.on('error')`) was attached *after* an early return that triggered when `res.statusCode !== 200`. If an HTTP error code (e.g., 500 or 503) was received and the server subsequently reset the connection before the stream completed, the unhandled `error` event would cause the Node.js process to crash (a Denial of Service).
**Learning:** Native Node.js `http`/`https` modules emit errors on streams asynchronously. If an error handler is conditionally bypassed via early returns (e.g., just returning `null` when a 5xx status is encountered without attaching `.on('error', ...)`), any subsequent network errors emitted by the `res` stream will bubble up as unhandled exceptions.
**Prevention:** Always attach `.on('error', ...)` handlers to both `req` and `res` objects *immediately* at their creation points, before any application-level checks or early returns.
