## 2026-07-29 - Uncontrolled Resource Consumption in NPM Registry Checks
**Vulnerability:** The CLI fetches package updates from the npm registry using `https.get` but does not bound the size of the HTTP response or properly dispose of unread stream chunks on error statuses.
**Learning:** This exposes the tool to Uncontrolled Resource Consumption (DoS) and potential socket memory leaks if the registry responds unexpectedly or maliciously.
**Prevention:** Always implement a maximum chunk length check in `res.on('data')` when consuming external data, call `req.destroy()` to abort oversized streams, and remember to call `res.resume()` on error paths to release socket resources.
## 2026-07-30 - Arbitrary File Overwrite via Symlink Attack
**Vulnerability:** The `install` command used `fs.cpSync` and `fs.copyFileSync` with `--force` without unlinking symlinks, potentially allowing an attacker to overwrite arbitrary sensitive files on the user's filesystem (like `~/.ssh/authorized_keys`) if they place a symlink in the target directory (e.g., `~/.claude/commands/akili-audit.md`).
**Learning:** When writing files recursively and allowing existing files to be overwritten, using `fs.cpSync` or `fs.copyFileSync` on a symlink target rewrites the referenced file rather than replacing the link. Checking existence with `fs.existsSync` is not enough because it follows symlinks.
**Prevention:** Use `fs.lstatSync` to check if a file exists, and if it is a symbolic link, remove it first using `fs.rmSync(targetPath, { force: true })` before copying.
## 2026-08-02 - Regex Engine Stack Exhaustion in ANSI Escape Stripper
**Vulnerability:** `scripts/parse_tests.js` ran its ANSI-stripping regex over unbounded `failureMessages` input. A multi-megabyte message exhausts the regex engine's backtrack stack (`RangeError: Maximum call stack size exceeded`), crashing the report step.
**Learning:** Measured on a ~10MB adversarial payload, the failure mode is input size, not pattern shape: the naive regex and the community-hardened `strip-ansi` pattern both throw the same `RangeError`, and both run in ~1ms on bounded input. Swapping the regex alone does not fix the crash.
**Prevention:** Bound unbounded input BEFORE running any regex over it (here `.slice(0, 2000)` ahead of the 120-char output truncation) — the same bound-every-external-read principle as the 2026-07-29 registry fix. Keep the community-hardened pattern as defense in depth against true backtracking blowups.
## 2026-08-03 - Shell Evaluation Hardening: execSync → execFileSync
**Vulnerability:** `bin/akili.js` built package-manager and version-check commands as shell strings for `child_process.execSync`. Review note: every interpolated value comes from a hardcoded whitelist (`npm`/`pnpm` — the user agent only selects probe order) or a literal, so there is no attacker-controlled input and no actual injection today; this is hardening against future call sites, not an exploitable CWE-78.
**Learning:** `execFileSync` with an args array removes the shell from the equation — but on Windows, patched Node (CVE-2024-27980) throws `EINVAL` when spawning `.cmd`/`.bat` without `shell: true`, so a naive swap silently breaks `npm.cmd`/`pnpm.cmd` invocation on modern Node.
**Prevention:** Prefer `execFileSync(bin, args)` over shell strings for anything dynamic; on `win32` pass `shell: true` (safe here because every argument is a static literal — never do this with untrusted args). Route stderr with `stdio` instead of `2>/dev/null` so the command stays shell-free on POSIX.
## 2026-08-04 - Symlink Defense Depth for Recursive Copies and File Writes
**Vulnerability (as reported):** nested destination symlinks inside directories copied by `fs.cpSync`, plus unprotected `fs.writeFileSync` targets (`~/.akili-specs-update.json` cache, Claude Code `settings.json`).
**Learning:** The behavior is **runtime-version-dependent, proven by the CI probe across the matrix**: on Node 18.20.8 (linux/darwin/win32), 20.11.1, and 22.12.0, `fs.cpSync(force)` *replaces* a nested destination symlink — the attack does not reproduce. On **Node 22.23.1 (all three platforms) it writes THROUGH the nested destination symlink** — the attack is real on current Node 22.x; the semantics changed inside the 22.x line. A single-version measurement (the reviewer's first pass) and an unmeasured assertion (the report) were both wrong in opposite directions; only the executed matrix held the truth. `fs.writeFileSync` follows destination symlinks on every version, so the cache/settings guards are unconditional hardening.
**Prevention:** Keep `removeTargetSymlinks` ahead of recursive copies (verified effective on all 6 matrix combinations), guard every `writeFileSync` destination with an `lstat` check, and pin filesystem semantics with the CI probe (`scripts/ci/install-symlink-probe.js`) — it asserts the defense and records raw `cpSync` behavior per platform/Node, so the next silent runtime change surfaces in CI instead of in the field.
## 2026-08-05 - TOCTOU Symlink Attack on File Writes
**Vulnerability:** The CLI checked if a target was a symlink using `fs.lstatSync` and removed it, and then subsequently called `fs.writeFileSync` to write to the cache or settings file. This introduced a Time-of-Check to Time-of-Use (TOCTOU) vulnerability where an attacker could create a symlink in the window between the `lstatSync` check and the `writeFileSync` operation, allowing them to overwrite arbitrary files on the filesystem.
**Learning:** Checking for and removing a symlink prior to a write operation is fundamentally flawed because it is not atomic. If the filesystem changes between the check and the write, `fs.writeFileSync` will blindly follow the symlink that an attacker managed to place there. Severity reported HIGH; realistically **LOW** — winning the race requires an attacker who can already create symlinks inside the user's home and `.claude/`, a position from which the race adds nothing (same reclassification pattern as the PR #3/#4 findings). Merged as hardening: the atomic write also buys **crash-safety** — a `settings.json` can no longer be left half-written by an interrupted process — which is arguably the more valuable property.
**Prevention:** Always use atomic operations when writing sensitive data. Write the data to a temporary file in the same directory (with a randomized name using `crypto.randomBytes`, opened `wx` so a pre-existing entry at the temp path fails the write instead of being followed) using `fs.writeFileSync`, and then use `fs.renameSync` to move it over the destination target. `fs.renameSync` replaces symlinks rather than following them, securely mitigating the TOCTOU attack.
## 2026-08-05 - TOCTOU Symlink Attack on copyFileSync
**Vulnerability:** The CLI copied individual files using `fs.copyFileSync` after checking/removing a symlink target with `lstatSync` via `removeTargetSymlinks`. Similar to the `fs.writeFileSync` issue, this creates a Time-of-Check to Time-of-Use (TOCTOU) vulnerability where a symlink could be created between the check and the actual copy operation.
**Learning:** Checking existence prior to a copy operation (`copyFileSync`) suffers from the same atomicity flaws as write operations. `fs.copyFileSync` will follow symlinks, which could potentially overwrite unintended system files.
**Prevention:** Use an atomic copy function when copying files. Write to a randomized temporary location using `fs.copyFileSync` with `fs.constants.COPYFILE_EXCL`, then rename it atomically to the destination using `fs.renameSync` which overwrites symlinks safely instead of following them.
